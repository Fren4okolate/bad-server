# Web-ларёк. Плохой сервер

Проектная работа: аудит безопасности интернет-магазина и административной панели.

- Репозиторий: https://github.com/Fren4okolate/bad-server
- Автор доработки: Иван Недбай
- Когорта: 42
- Курс: Фулстек расширенный
- Публичное развёртывание на сервере не выполнялось.

Стек: React, TypeScript, Vite, Express, MongoDB, Nginx, Docker Compose.

## Запуск через Docker

Нужны Docker с Compose v2 и свободный локальный порт 80.

```bash
git clone https://github.com/Fren4okolate/bad-server.git
cd bad-server
docker compose up --build -d
docker compose exec -T backend npm run seed
```

Откройте http://localhost/. Вход: http://localhost/login; административная панель: http://localhost/admin.
MongoDB и backend доступны только внутри сети Compose. Демонстрационный сайт слушает `127.0.0.1:80`.

`seed` импортирует товары и создаёт демонстрационных пользователей с bcrypt-паролями. Повторный запуск не меняет пароли существующих пользователей с bcrypt. Исходный дамп пользователей с MD5 использовать нельзя; подробности в [.dump/README.md](.dump/README.md).

| Роль | Email | Демонстрационный пароль |
| --- | --- | --- |
| Администратор | admin@mail.ru | password |
| Покупатель | user1@mail.ru | password1 |

Эти учётные записи предназначены только для локальной проверки; `seed` запрещён при `NODE_ENV=production`.

```bash
docker compose logs --tail=100
docker compose down
```

## Разработка без Docker

Нужны Node.js 22+ и MongoDB 7. Установите зависимости:

```bash
npm ci --prefix backend
npm ci --prefix frontend
cp backend/.env.example backend/.env
npm run build --prefix backend
npm run seed --prefix backend
npm run dev --prefix backend
```

В другом терминале запустите `npm run dev --prefix frontend`. Откройте http://localhost:5173. Vite проксирует `/api` на порт 3000. В `backend/.env` укажите доступный `DB_ADDRESS`; по умолчанию используется `mongodb://127.0.0.1:27017/weblarek`.

## Исправления безопасности

- Комментарии очищаются `sanitize-html` на сервере и DOMPurify перед HTML-выводом. Обычные поля выводятся средствами React; ссылки и пути изображений ограничены.
- Все изменяющие запросы, включая вход, регистрацию, выход и обновление токенов, требуют CSRF-токен, привязанный к серверной сессии. Сессии хранятся в MongoDB. Клиент передаёт токен в `X-CSRF-Token`.
- Для тела, параметров и query используются схемы Joi, разрешённые поля и ограничения длины. Операторы MongoDB и вложенные ключи из пользовательского ввода отклоняются; выражения поиска экранируются.
- Пароли хешируются bcrypt; роли проверяются по базе. Покупатель видит только свои заказы. Обновление профиля не позволяет менять роли, пароль или токены.
- Access JWT действует 10 минут, refresh JWT — 7 дней. Типы токенов различаются; refresh-токен хранится как HMAC и потребляется атомарно, предотвращая повторное и одновременное использование.
- Загрузка изображений доступна администратору: файл 2 КБ–10 МБ, не более 16 млн пикселей. Sharp декодирует изображение и перекодирует его в WebP под случайным именем. Временные файлы удаляются; публична только директория изображений.
- Общий лимит API — 40 запросов в минуту на IP, авторизация — 20, загрузка — 10. Каталог кешируется на 30 секунд с очисткой при изменениях; статика — на сутки. `/health` доступен при превышении лимита.
- Ограничены JSON (32 КБ), глубина объектов (10), количество товаров в заказе (100), размер страницы (10), время запросов к MongoDB и HTTP. Логи Docker ротируются.
- Обновлены зависимости, исправлены ошибки линтинга, типизации, пагинации и оформления заказа. Добавлены проверки безопасности и Docker в GitHub Actions.

Подробности, ограничения и результаты проверок: [отчёт аудита](security_best_practices_report.md).

## Проверки

```bash
npm run audit
npm run lint
npm run build
TEST_MONGO_URL=mongodb://127.0.0.1:27019 npm test
npm run test:load -- http://localhost/api/product 1000 40
```

`npm test` создаёт отдельную базу со случайным именем и удаляет только её после проверки. `TEST_MONGO_URL` должен указывать на тестовый MongoDB без имени базы. Нагрузочный скрипт принимает только локальный адрес; ответы 429 ожидаются и подтверждают работу ограничения запросов.

В GitHub Actions сохранена проверка из репозитория `Yandex-Practicum/tests-bad-server`; дополнительный workflow проверяет сборку, ESLint, npm audit, 11 регрессионных сценариев и полный запуск через Compose. Изменения находятся в `review`; после успешных проверок pull request объединяется в `main` через **Squash and merge**.

## Настройки для публикации

Демонстрационный Compose рассчитан на локальный HTTP. Перед публикацией настройте HTTPS, `NODE_ENV=production`, `COOKIE_SECURE=true`, разрешённый origin, отдельные сильные секреты `AUTH_ACCESS_TOKEN_SECRET`, `AUTH_REFRESH_TOKEN_SECRET`, `SESSION_SECRET` и пароль MongoDB. `TRUST_PROXY=1` допустим только при недоступном извне backend и доверенном единственном прокси, который перезаписывает `X-Forwarded-For`.

Пример генерации каждого секрета: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Секреты хранятся в окружении, `.env` исключён из Git. В development без заданных секретов используются случайные значения: после перезапуска потребуется повторный вход.
